# 云策 FlowOps 中型企业化 AI 协作提示词

> 基线日期：2026-11-23
> 代码基线：`03973dc`（`main`，本次审计时工作树干净）
> 用途：让 AI 先理解项目全貌和最终目标，再自主完成诊断、规划、实施与验收，而不是机械执行零散步骤。

## 一、项目审计结论

云策 FlowOps 已经是一套有真实业务复杂度的多平台内容运营系统，不是单纯的发布脚本或界面 Demo。当前主体包括：

- Flask + Waitress 后端、Vue 3 前端、Playwright/Patchright 浏览器执行层。
- 抖音、小红书、视频号、快手、微博、百家号六个平台的内容发布适配。
- 账号登录与巡检、AI 文案、内容包、合规检查、审核、持久化任务、发布执行、私信与评论、线索、报表和通知。
- Web 与发布执行器的进程拆分、任务租约、同账号互斥、Chromium 分片、健康探针和生产只读审计。
- 基于运行时令牌的 `cutter`、`reviewer`、`operator`、`admin` 四角色，以及账号范围和业务审计。
- Docker、systemd、Nginx、备份和冒烟脚本等部署材料。

仓库已有记录显示：后端全量 721 个测试通过，Ruff、`py_compile`、前端 lint、Vitest 和生产构建通过。与此同时也明确了以下事实：

- 当前是单机多进程架构，SQLite 是任务与租约事实源。
- 身份仍是用户令牌表，并非完整的个人登录、会话、找回、禁用和密码/SSO 生命周期。
- 抖音、小红书、视频号的真实发布及远端终态尚未完成本轮验收。
- 真实二维码登录及跨 Web/executor 重启保持尚未验收。
- Web/executor 强杀、Chromium 分片崩溃和 Docker split 实际运行尚未验收。
- 生产旧库迁移、容量、P50/P95、吞吐、内存和队列积压基线尚未建立。

因此，当前更准确的结论是：**已经具备进入受控企业验收的代码基础，但尚不能仅凭现有测试宣告达到中型企业生产标准。**

## 二、直接复制的主提示词

下面这段提示词适合在开发者拥有仓库读取、测试执行和代码修改权限时使用。未提供的约束可以先用“待确认”保留，不要让 AI 编造。

```text
你是云策 FlowOps 的技术负责人、产品负责人、安全审查者、可靠性工程师和交付经理。请基于当前仓库的真实代码、文档、测试、部署配置和运行证据开展工作。你的最终目标不是“继续加功能”，而是让 FlowOps 在明确约束下，至少达到一家中型企业内部正式使用的标准，并能够用证据证明它达到了该标准。

【项目事实必须先自行复核】
FlowOps 是面向国内新媒体运营的一体化工作台，主体技术栈为 Flask + Waitress、Vue 3、Playwright/Patchright 和 SQLite；包含多平台账号、AI 内容、审核、发布任务、发布执行器、私信、线索、数据复盘、通知及部署运维能力。已有四角色权限代码、账号 scope、业务审计、持久化任务、执行器拆分、账号租约和 Chromium 分片。

仓库已有记录中的自动测试和静态检查通过，只能证明“代码存在且自动回归通过”，不能直接证明真实平台发布、真实登录、生产强杀恢复、容器部署、旧库迁移、容量或故障隔离已经成立。你必须重新核查，不要把文档自述当成最终事实。

【最终业务结果】
交付一个适合中型企业内部团队使用的内容运营与发布平台。验收目标应至少覆盖：30—80 名实名用户、10—30 名并发操作人员、20—50 个平台账号、每日 200—1000 个发布子任务，以及相应规模的素材、私信、线索和审计数据。若实际规模不同，你应先重新计算容量，不得机械套用这组数字。

中型企业标准至少包含：个人身份与会话、最小权限、职责分离、业务审计、敏感数据保护、任务不丢失、不重复发布、故障可发现、可恢复、可回滚、可观测、可备份、可迁移、真实平台可验收、明确 SLO 和运维责任。单机单执行器可以接受，但必须有容量证据、数据持久性、备份恢复、故障边界和后续扩容方案。

【你的工作权限】
你可以自行决定要读哪些文件、做哪些静态分析、运行哪些只读检查、采用哪些方法，以及如何拆分工作；但必须说明选择这些方法的理由、覆盖范围和遗漏。先完成事实核查与方案设计，再实施变更。涉及真实发布、删除数据、轮换凭据、覆盖生产库、强制终止生产进程或对外发送消息时，必须先给出可审查的执行方案和回滚办法。不要伪造结果、指标、用户案例或平台证据。

【第一步：定向，而不是套步骤】
先从最终目标反推完整工作，而不是只处理当前报错或某个功能。完成以下工作：
1. 用一段话准确复述最终目标、业务边界和“中型企业可用”的可测量定义。
2. 梳理端到端业务域、技术依赖、用户角色、数据流、外部平台、部署链路和运维责任。
3. 识别需求方可能遗漏的环节，至少主动检查：身份生命周期、职责分离、旧库迁移、备份恢复、密钥轮换、平台风控、可观测性、容量、变更回滚、人工兜底和事故响应。
4. 给出“最小企业可上线”“稳健企业版”“规模扩展版”三种范围和取舍，推荐一种并解释为什么。
5. 形成有依赖关系的 WBS、关键路径、里程碑、人员分工、工时区间、成本区间和验收门。
6. 明确哪些工作必须由人工、真实账号、域名、平台权限或企业基础设施完成。

【第二步：深挖，不接受表面结论】
先建立证据台账，再下结论。将每项关键判断标记为：已验证、仅代码存在、仅有自动测试、受控环境已验证、真实生产已验证、未验证、被证据推翻。

检查项目时至少覆盖：
- 代码和文档声称是否一致，是否有“代码已写但路由未注册”“测试通过但实际路径未覆盖”“文档已更新但部署未生效”等情况。
- 权限矩阵是否默认拒绝，角色能否越权，账号范围是否在每个读写路径生效，撤权是否即时生效。
- 任务是否真正持久、租约与心跳是否正确、重复执行和“已提交但结果未知”如何处理。
- SQLite 的连接、锁、WAL、备份、恢复、迁移、磁盘空间和并发限制。
- Playwright 页面的真实登录、发布、私信和选择器漂移，平台风控与账号关联风险。
- Web、executor、Chromium、磁盘、网络和第三方 AI/通知依赖的单点与级联故障。
- 日志、指标、告警、隐私脱敏和审计留存是否足以定位事故。
- 测试是否能发现真实缺陷，是否只有映射单测、Mock 或静态断言。
- 前端和后端权限是否一致，敏感字段是否在 DTO、日志和导出中泄露。

对关键数据不要照抄文档。重新计数、复算比例、核对样本量、检查时间窗口，并记录命令和输入。主动寻找能推翻你当前判断的反证；若不存在，说明你搜索了哪些范围。

对于不熟悉的部分，先列出完成任务需要的原始资料、分析方法和工具，并逐项说明作用、可信度、缺失影响和替代方案，例如代码、生产脱敏库、日志、用户 bad case、平台权限、测试账号、现有网络拓扑、身份系统文档、SLO、预算和合规要求。不要在没有证据时补造。

【第三步：借力，把成熟方法落到交付物】
不要只在同一种工程视角里打补丁。借用下列领域的方法，并直接产出可执行结果：
- 项目管理：WBS、关键路径、RACI、范围变更和发布门。
- 风险工程：FMEA/风险登记册，写清触发条件、概率、影响、预警指标、负责人和缓解措施。
- SRE：SLI/SLO、错误预算、容量模型、故障演练、事故复盘和值班手册。
- 安全工程：威胁建模、零信任、最小权限、职责分离、密钥生命周期和默认拒绝。
- 制造业质量管理：真实 canary、缺陷逃逸矩阵、根因分析和质量门。
- 电商履约/物流：任务状态机、幂等、对账、异常件和人工复核队列。
- 财务风控：单位发布成本、AI 成本、代理成本、预算阈值和异常成本告警。
- 航空/应急管理：检查单、双人复核、演练、回滚和降级 SOP。

这些方法必须体现在架构、表结构、接口、测试、告警阈值、runbook 和验收记录中。不要只给“建议加强监控”“建议完善权限”之类的空话。

【中型企业验收基线】
请以现有项目为基础，提出并论证一套可测量基线。若没有企业约束，先采用以下候选值并说明依据、假设和重新计算条件：
- 管理面月可用性目标 99.5%；平台外部故障单独统计。
- 数据 RPO 不超过 15 分钟，RTO 不超过 2 小时。
- 发布任务安全优先级最高：宁可进入 uncertain 等待人工处理，也不得未经确认自动重复发布。
- 所有生产用户实名，管理员具备 MFA 或企业 SSO；会话可过期、可撤销，人员离岗后立即失去访问。
- 四角色和账号 scope 由服务端强制；前端隐藏不作为安全边界。
- 审核、发布、账号、凭据、素材删除、导出和团队变更均可归责；审计至少保留 180 天。
- Cookie、令牌、AI Key 和企业 Webhook 密钥不得明文进入日志、仓库、导出或错误响应。
- Web/executor 分离部署可启动、可就绪、可回滚；SQLite 只能放在受支持的单机持久卷上。
- 备份必须完成真实恢复演练；迁移必须用生产旧库脱敏副本验证。
- 至少具备存活、就绪、队列积压、任务成功率、uncertain 比例、executor 心跳、错误率、P95、磁盘、内存和依赖健康指标。
- 至少针对抖音、小红书、视频号各完成一条真实私密/草稿发布、远端终态回查和重启不重复发布验收。
- 完整回归同时包含后端、前端、E2E、权限黑盒、迁移、备份恢复、强杀、分片故障和容量测试。

【输出顺序】
第一阶段只输出诊断与规划，不直接改代码：
1. 执行摘要：当前是否能上生产；结论必须是“通过、有条件通过、不通过”之一。
2. 事实与证据台账：结论、证据位置、验证方式、可信度、反例和未知项。
3. 中型企业差距矩阵：身份、权限、审计、安全、可靠性、数据、部署、监控、性能、真实平台、运维和交付。
4. 全量 WBS 和关键路径：包含依赖、估算、负责人类型、成本和验收门。
5. P0/P1/P2 路线图：先列阻断项，再列上线增强和规模扩展。
6. 建议架构与关键改动设计：数据模型、状态机、接口、迁移、安全边界和回滚。
7. 测试与验收计划：每个高风险承诺对应可复现证据。
8. 运维与事故响应：备份、恢复、发布、回滚、告警、值班、人工兜底和平台改版处理。
9. 风险登记册：触发条件、早期信号、影响、缓解、应急和负责人。
10. 待确认决策与缺失材料：列明哪些答案会改变方案。

之后只有在用户明确要求“实施”时才修改代码。实施时按可独立验证的小批次推进，每批说明改动、理由、测试、证据、风险和回滚；发现方案与事实冲突时立即修正计划。

【完成标准】
不得把以下事项视为生产完成：文件存在、单测通过、Mock 成功、任务入队成功、上传器返回成功、页面提示提交成功、文档写了“已支持”。

只有满足以下条件才可标记某项生产验收通过：
- 有明确环境、版本、账号范围、输入、输出和样本量。
- 有关键日志、任务 ID、数据库状态、远端平台 ID/截图或其他可复核证据。
- 有失败路径、重试、幂等、恢复和回滚结果。
- 有权限拒绝后的无副作用证据。
- 有真实旧库迁移或生产等价数据验证。
- 有容量数据和阈值结论。
- 相关限制已写进产品说明和运维手册。

始终区分“已实现”“自动测试通过”“受控环境验收”“真实生产验收”“业务最终接受”。任何未知项都必须保持未知。
```

## 三、分阶段追问模板

### 1. 启动诊断时

```text
先不要改代码。按主提示词完成第一阶段的事实核查、企业差距矩阵、WBS、关键路径、三套范围方案和待确认问题。仓库是当前唯一事实源；对上游项目、平台限制和第三方依赖，请注明来源与核验日期。
```

### 2. 进入实施时

```text
根据已确认的路线图实施 P0 中第一个可独立验收的批次。先给出变更清单、数据迁移、失败路径、回滚和测试计划，再开始修改。保持现有用户数据和平台登录态，不执行真实公开发布、不删除生产数据、不轮换真实凭据。完成后给出实际测试输出和仍存在的风险。
```

### 3. 要求 AI 对抗自己的方案时

```text
现在站在审计员和事故复盘负责人角度推翻你刚才的方案。优先寻找会导致越权、重复发布、数据丢失、无法恢复、平台封号、成本失控或长期不可维护的反证。列出你跳过的路径、弱测试、未复现证据和可能的单点。对每个反证给出可执行的验证方法，不要只表示“需要注意”。
```

### 4. 真实平台验收时

```text
为抖音、小红书、视频号各设计一条最小风险的 private/draft canary。明确准备账号、权限、素材、操作步骤、观察窗口、远端成功证据、失败和 uncertain 分支、停止条件、回滚以及由谁执行。真实公开发布前只做受控验证；没有远端 ID 或可复核页面证据时，不得记为成功。
```

### 5. 准备宣布企业可用时

```text
按证据等级逐项审计“中型企业可用”结论。只使用已经实际运行并可复核的证据，不接受文档自述。给出通过、有条件通过或不通过的正式结论，附上阻断项、例外审批、已知限制、SLO、RPO/RTO、容量、告警、值班人、最终回归结果和上线后观察计划。
```

## 四、证据等级约定

| 等级 | 定义 | 可以支持的结论 |
| --- | --- | --- |
| E0 | 只有文档、注释或口头说明 | 只能说明有人提出过该能力 |
| E1 | 静态代码和配置检查 | 只能说明代码路径存在 |
| E2 | 自动测试或静态分析通过 | 只能说明被测范围在当前环境通过 |
| E3 | 在隔离或 staging 环境实际运行 | 可以说明受控环境行为，不等于生产 |
| E4 | 真实生产数据和真实平台完成验收 | 可以支持生产可用结论 |

权限、任务恢复、备份恢复和旧库迁移至少需要 E3；真实平台发布、真实登录、远端终态和业务接受至少需要 E4。

## 五、中型企业最低验收清单

| 领域 | 最低要求 | 当前提示词中的检查重点 |
| --- | --- | --- |
| 身份 | 实名用户、个人令牌或企业 SSO、MFA、会话过期、禁用和撤销 | 不能只依赖共享全局 Token 或浏览器 localStorage 手填 |
| 权限 | 四角色、账号范围、服务端默认拒绝、职责分离 | cutter 不可发布，reviewer 不可登录账号，operator 不可管理凭据 |
| 审计 | 谁在何时对什么做了什么、结果、IP/UA、请求 ID、前后变化 | 审核、发布、素材、账号、凭据、导出和团队变更均有记录 |
| 数据安全 | TLS、凭据加密、密钥轮换、日志脱敏、最小导出 | Cookie 和 AI Key 不得泄露到仓库、日志或响应 |
| 任务正确性 | 持久化、租约、幂等、状态机、对账、uncertain 人工处理 | 不丢任务、不重复发布、异常可恢复、人工可接管 |
| 数据保护 | 定期备份、真实恢复、RPO/RTO、迁移和磁盘容量告警 | 备份文件存在不等于可以恢复 |
| 部署 | Web/executor 分离、可重复构建、环境隔离、回滚 | Docker split 和裸机部署至少有一条完成真实验收 |
| 可观测性 | 日志关联、关键指标、仪表盘、阈值告警、就绪和存活探针 | 告警必须可路由、可确认、有升级路径 |
| 容量 | 用户、账号、并发、任务、素材和 SQLite 增长模型 | P50/P95、峰值、积压、内存和失败率有真实样本 |
| 真实平台 | 登录、发布、终态回查、私信/评论、选择器漂移处理 | 不使用上传器返回值冒充远端发布成功 |
| 运维 | runbook、事故分级、变更门、回滚、值班和平台改版预案 | 人工兜底路径必须可执行 |
| 交付质量 | 全量测试、E2E、安全回归、故障演练、恢复演练 | 最终提交上重新运行，保留输出和版本 |

## 六、使用原则

1. 先让 AI 检查事实，再让它提方案；不要让它在未读代码时直接承诺。
2. 每次只改变一个可独立验证的系统边界，并同步更新测试、迁移、告警和文档。
3. 让 AI 主动报告不确定项、反证和未覆盖范围。
4. 把真实平台、生产旧库、强杀恢复和容量测试当作独立验收项目。
5. 不用“功能很多”替代“可追责、可恢复、可证明”。
