## 1. 历史 20 个失败测试的分类与处置

全量测试重新执行后已经没有失败。下表是对上一轮 20 个失败证据的分类，用于说明当初为什么修、修到什么边界；它不是当前仍存在 20 个失败的陈述。由于成功重跑后 pytest 会清空 `lastfailed`，本文不虚构逐条测试名和计数。

| 历史失败组 | 分类 | 判断依据 | 优先级 | 最小修复范围 | 企业级验收影响 |
| --- | --- | --- | --- | --- | --- |
| DM 测试替身的方法签名与实现不一致 | A. 纯旧债 | 失败发生在 fake 接口调用约定，没有证据表明真实 DM 发送链路因此失败 | P3 | 只扩测试替身参数，不改业务协议 | 不阻塞；但需保持测试替身与接口一致 |
| 媒体安全测试访问真实 DNS，或 fake HTML 响应缺少状态字段 | A. 纯旧债 | 测试隔离不完整，导致网络或响应对象本身制造失败，不是媒体安全策略判定错误 | P3 | 固定 mocked URL 校验、补齐 FakeResponse 状态码 | 不阻塞；否则测试会受网络环境影响 |
| 历史账号库缺少暂停字段 | B. 可能掩盖新问题 | 若只是测试库旧，是夹具漂移；若生产也是旧库，则启动后 DM 账号读取会报列缺失 | P1 | 读取时兼容历史上存在的列；再用真实旧库副本验证启动与 DM 列表 | 当前代码已兼容并通过全量测试；仍应在上线前拿生产库副本做一次 schema 兼容检查，不能只凭测试通过下结论 |
| `GET /deleteFile?id=...` 未受发布权限映射保护 | C. 产品缺陷 | GET 删除路径可绕过 publish 权限判断，属于授权边界缺口，不是断言问题 | P0（已修复） | 把该路径纳入 publish 权限判定，并补正反授权测试 | 修复前阻塞企业级验收；当前测试全绿后仍需在生产权限矩阵中复验 |

### 1.1 当前处置结论

- A 类：没有未处理的业务修复项。测试夹具应与真实接口约束同步，避免再次出现“测试假失败”。
- B 类：代码兼容修复已通过测试，但“生产旧库是否含所需列”仍需用脱敏库副本验证。该项不要求改业务架构。
- C 类：修复已进入当前全量测试套件。企业验收还应分别用管理员、运营、无 publish 权限用户访问删除路径，证明返回码和实际文件未变。
- 当前没有证据支持还有 A、B 或 C 类开放失败，因此不再把旧的 20 failed 当作当前发布阻塞项。

## 2. 未验证项的风险排序与最小验证设计

建议的验证顺序是：先确认部署形态可启动，再做登录，再做真实发布，再做故障恢复。风险严重度最高的是真实发布和登录；执行顺序需要先保证容器与路由能运行。

本轮五项里“可以延后”为空：Docker、登录和真实发布是三平台上线门槛；两类崩溃至少要在灰度期完成。不能因为已有租约单测就把真实恢复当作已验收。

### 2.1 Docker split 实际运行

- **档位：上生产前必须验证。**
- **验证成本：低到中。** 约 0.5 到 1 人日；无需真实发布即可取得首轮证据。
- **环境：** 一台与生产同类的 Linux 主机，安装 Docker Compose v2；`.env.deploy` 和持久化目录已准备；不需要把本地 Cookie 或媒体上传到测试主机。
- **最小方案：** 在空的验收数据目录启动 `docker-compose.yml + docker-compose.split.yml`，运行 `bash deploy/verify_split.sh`。该脚本只读检查 compose 解析、两个容器、进程角色、同一镜像、`/health/ready`、executor 心跳和生产审计 gate，不创建任务，也不杀进程。
- **通过标准：** `compose config` 成功；`yunce` 和 `yunce-executor` 同时 running；角色分别为 `web` 和 `executor`；两容器镜像 ID 相同；`/health/ready` 返回 200；审计 gate PASS。
- **失败回滚：** 停止 executor，保留 `deploy/data`，回到不加载 split 覆盖文件的单容器 `all` 模式。不要删除数据目录或覆盖现有 SQLite、Cookie、素材。
- **当前限制：** 本机没有 Docker；`verify_split.sh` 已通过 Git Bash 的 `bash -n`，并验证会因缺少 Docker 明确失败。compose 和容器仍未实际执行。

### 2.2 真实二维码登录与跨重启保持

- **档位：上生产前必须验证。**
- **验证成本：中。** 每个平台约 0.5 人日，另需人工扫码；视频号若有多个频道，还要逐频道检查。
- **环境：** 测试账号、可访问平台的测试主机、能展示 SSE 二维码的浏览器、可重启的 Web 进程或容器。
- **最小方案：** 抖音、小红书、视频号各选一个专用账号扫码；登录后在刷新页面、重启 Web、重启 executor 三个时点检查账号记录与平台创作者页。视频号必须确认每个频道有独立账号记录、Cookie、指纹和代理归属。
- **通过标准：** 用户信息可在刷新后读取；重启后发布执行器仍读取到同一账号上下文；不同账号之间没有串号；登录态失效时状态能明确标异常，而不是假装在线。
- **失败回滚：** 重启前备份 `cookiesFile/` 和账号库；失败时恢复备份，删除本次新建的无效账号记录，暂停该账号自动动作。不要覆盖其他账号的 Cookie。

### 2.3 真实平台发布与远端终态回查

- **档位：上生产前必须验证。** 这是最高业务风险项。
- **验证成本：高。** 三个平台合计约 2 到 4 人日；受网络、账号风控、审核和远端延迟影响。
- **环境：** 三个平台各一个专用测试账号；短小且无版权风险的独立视频；平台允许的 private/draft 可见性；人工能够在平台后台核对远端记录。
- **最小方案：** 每个平台发布一条私有或草稿内容。记录入队时间和 job/item ID；等待真实远端记录，再由追踪器或人工核对远端 ID、状态和最终可见性。
- **通过标准：** 远端能查到对应作品；终态与本系统一致；成功只在远端终态确认后写入；平台不支持回查时停留在 `submitted`，不能被统计为成功；同一幂等键不会因为重启而重复发表。
- **失败回滚：** 先暂停发布执行器，再在平台后台撤回、删除或转为私有；未知提交保持 `uncertain`，禁止自动重发；发布前保存账号 Cookie 和任务库快照。
- **当前结论：** 未验证，不能说真实发布可用，也不能按上传器返回值宣传发布成功。

### 2.4 Web/executor 强杀恢复演练

- **档位：上生产前必须验证启动和空闲恢复；发布过程中强杀可在灰度期复核。**
- **验证成本：中。** 约 1 人日，需要可丢弃的验收栈。
- **环境：** split 验收主机或两个本地进程；至少一个可安全发布的测试账号；只使用验收任务。
- **最小方案：** 先分别强杀 Web 和 executor，确认容器/进程监控能重启、Web 就绪检查能识别 executor 缺失、executor 心跳恢复。然后用一条私有内容在发布中强杀 executor，检查未提交项回到可执行状态、已提交但结果未知项进入 `uncertain`。
- **通过标准：** 不重复发布；租约不会被错误 token 续期；Web 恢复后 API 可用；executor 恢复后接管 pending；uncertain 可追溯并有 job/item/event 证据。
- **失败回滚：** 重启两个进程，保持任务事实库不变；将不确定项交由人工核对，暂停自动重试；必要时回到单容器 `all` 模式恢复服务。

### 2.5 Chromium 分片崩溃恢复演练

- **档位：可以灰度期验证。**
- **验证成本：中。** 约 0.5 到 1 人日。
- **环境：** 隔离 staging，`FLOWOPS_SHARED_BROWSER=1`、至少 2 个分片、两个稳定映射到不同分片的测试账号。
- **最小方案：** 先建立两个账号上下文，仅终止一个 Chromium 子进程；分别让两个账号执行非公开发布或登录态只读探针，观察崩溃分片重建和另一分片持续工作。
- **通过标准：** 崩溃分片下一次访问可重建；另一分片未整体中断；失败任务不伪成功；崩溃前后浏览器分片 ID/状态和任务结果可追溯。
- **失败回滚：** 重启 executor；临时设置 `FLOWOPS_SHARED_BROWSER=0` 回到 persistent 模式；不得把单账号隔离降级当作已解决整机 OOM。

## 3. 性能基线的测量方案

### 3.1 指标定义与采集点

| 指标 | 定义 | 当前采集点 | 使用限制 |
| --- | --- | --- | --- |
| 队列等待 | `started_at - COALESCE(scheduled_at, created_at)` | `_run_claimed_job()` 领取 item 并写 `started_at`；`production_audit.py` 聚合 | 同进程 `_account_lock` 等待发生在 `started_at` 之前，可通过总等待差分析 |
| 开始到提交标记 | `submitted_at - started_at` | `_run_claimed_job()` 在调用 `_execute_item()` 前写 `submitted_at` | 这是防止崩溃重复发布的“调用前标记”，不是平台已接收，也不是完整上传耗时 |
| 成功端到端 | `finished_at - created_at`，仅 `status='success'` | `_record_publish_result()` 和追踪器写 `finished_at`；`production_audit.py` 计算 P50/P95/max | 包含排队、浏览器、平台审核/追踪；不能当作单纯浏览器速度 |
| 全部终态端到端 | 终态 item 的 `finished_at - created_at` | 同上，状态集合为 success/failed/uncertain/skipped/cancelled/draft/submitted | 用于用户等待和尾延迟，不替代成功率 |
| 吞吐 | 窗口内 `finished_at` 的终态 item 数 / 窗口小时数 | `production_audit.py` 的 `terminal_items_per_hour` | 报告窗口内完成量；不能用某一时刻的当前状态冒充吞吐 |
| 成功率 | 窗口内完成且状态为 success / (success+failed+uncertain) | `production_audit.py` 的 `rates` | skipped/cancelled/preflight 不计入发布尝试；必须同时报告 uncertain |
| P95 | 最近秩法排序后第 `ceil(0.95*n)` 个样本 | `production_audit._percentile()` | 样本少于 20 时只能当方向值，不能对外作 SLA 证明 |
| 浏览器并发 | `browser_pool.status()` 的 active/peak/max | `browser_slot`/`browser_slot_async` 获取与释放 | 只代表上下文槽，不等于平台成功并发 |
| 分片内存 | executor 容器 cgroup `memory.current`，以及 Chromium 子进程 RSS 的最大值/中位数，每 10 秒采样 | 当前 `utils/shared_browser.status()` 只暴露分片连接状态，不暴露逐分片 RSS；首轮由容器进程树采样 | 目前不能从 Playwright 公共 API 稳定取得每分片主进程 PID，不能把容器总量冒充单分片 RSS |
| split 内存 | Web 与 executor 两个容器的 `memory.current`/RSS | `docker stats --no-stream` 或 cgroup 文件，每 10 秒一次 | 需同时记录容器数、分片数、上下文数和 worker 数 |

性能报告至少按平台、账号、素材大小、内容类型、任务阶段拆分。只报一个总 P95 会掩盖单平台慢、视频大小差异和账号限速。

### 3.2 单机最小压测

**真实浏览器 canary（主要基线）**

- 账号：3 个专用测试账号（抖音、小红书、视频号各 1 个）；不混入运营账号。
- 任务：30 个独立 item，每平台 10 条；使用不同标题和幂等键，优先 private/draft，结束后清理。
- 并发：`FLOWOPS_PUBLISH_WORKERS=2`，`FLOWOPS_MAX_BROWSERS=4`，`FLOWOPS_SHARED_BROWSER_SHARDS=2`；这是当前保守默认，不先靠扩大并发制造风险。
- 时长：预热 5 分钟，稳定运行至少 60 分钟；等待远端终态完成或明确超时。
- 采样：每 10 秒记录两容器 memory.current/RSS、active/peak contexts；每轮结束运行 `production_audit.py --hours 1`（或按实际窗口）。
- 重复：至少 2 次，建议 3 次；保留每次 JSON，报告 n、P50、P95、成功率、uncertain 和内存峰值。

**无平台结构压测（辅助）**

用测试替身提交 100 个 job、每个 1 个 item，持续 60 秒，验证队列投递、租约和状态转换本身没有明显瓶颈。该结果只代表调度开销，不能证明真实平台吞吐。

### 3.3 all 模式 vs split 模式

1. 同一台主机、同一镜像、同一账号集、同一素材大小、同一任务模板和同一并发配置。
2. 先运行 `all` 至少两轮，再运行 split 至少两轮；轮次交替或跨时段重复，降低平台侧波动。
3. 每轮记录：30 个完成量、success/failed/uncertain、queue P95、success E2E P95、terminal E2E P95、两容器内存峰值、Chromium 分片数。
4. 使用相同窗口口径比较；不要拿 all 的 6 小时窗口和 split 的 24 小时窗口比较。
5. 在基线建立前只报告“已采集”或“未采集”。建立后也报告样本量、时间窗、平台版本和环境，不能只给一个百分比。

### 3.4 对外沟通口径

基线建立前：

> 当前已完成任务队列、账号互斥、执行器分离和浏览器分片等代码加固；真实平台发布、生产重启和性能尚未验收，目前没有可对外声明的吞吐或延迟提升百分比。

采集完成后：

> 在 2026-XX-XX 的同一主机和同一 30 条私有发布样本下，split 模式与 all 模式的 P50/P95、成功率、uncertain 数和内存峰值分别为……；样本仅覆盖……，不代表其他平台或生产 SLA。

## 4. 新缺口优先级

| 能力 | 优先级 | 判断 |
| --- | --- | --- |
| 剪辑、审核、运营、管理员四角色独立权限闭环 | **企业级验收前 P0** | 目标用户直接包含剪辑和运营。只有 admin/operator/viewer 无法保证剪辑人员不能发布、审核人员不能登录账号，也无法形成素材、审核、发布、账号管理之间的最小职责分离；这是产品边界，不是规模优化 |
| leader election | P1，先于多调度实例 | 当前一个 Web 加一个 executor 可由 job lease 和 SQLite 事实成立；当出现第二个 scheduler/tracker 实例时必须补，否则升级为可靠性风险 |
| 多 executor + 跨主机 SQLite | P2，规模阶段 | SQLite 共享文件不适合跨主机；增加 executor 前应先完成数据库/队列迁移和故障模型，当前没有证据支持横向扩容 |
| 横向扩容 | P2，依赖前两项 | 只有在多 executor、leader election、跨主机事实存储和容量基线都成立后才可讨论 |

四角色权限闭环是 **P0** 的依据不是代码复杂度，而是用户上线条件：没有独立 editor 权限，剪辑人员若只能通过 operator 使用，就拥有发布能力；没有独立 reviewer，审核人员就可能继承账号/登录范围。两个条件任一成立，企业级验收就不应通过。

## 5. 企业级差距矩阵

| 维度 | 当前状态 | 企业级标准 | 差距 | 补齐路径 | 预计工作量 |
| --- | --- | --- | --- | --- | --- |

## 6. 性能基线与 bad case 的当前填写

### 6.1 性能基线

- 单次发布平均耗时：未测。
- 并发发布数量：未测。
- P50/P95 延迟：未测。
- 高峰队列积压：未测。
- Chromium 分片 RSS、容器内存峰值：未测；当前审计工具能从 SQLite 计算队列和终态指标，但当前没有新的样本。

结论：全部未测。任何百分比提升、容量提升或“更快”的说法都必须等待同口径 before/after 数据。

## 7. 验收执行顺序

1. 在 Linux staging 执行 `bash deploy/verify_split.sh`，先证明 split 可启动、可就绪、可审计。
2. 用三个专用账号完成真实扫码，重启 Web/executor，复核登录态和账号隔离。
3. 每个平台做一条 private/draft canary，等待远端终态；没有远端证据不算成功。
4. 在 staging 做 idle/kill 和一条私有发布中的强杀，确认续租、恢复和 uncertain。
5. 在 staging 做 Chromium 分片崩溃探针，确认其他分片和账号不被错误污染。
6. 用同口径 3 账号、30 item、2 worker、2 分片采集 all/split 性能数据。
7. 最后用测试矩阵验收四角色权限；在此之前不面向剪辑/审核团队开放生产权限。
